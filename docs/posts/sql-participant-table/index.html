Why run a feasibility assessment?

One of the most expensive mistakes in research is asking a question that the available data cannot answer.

Before fitting a model (or even writing a proposal or statistical analysis plan), I first perform a cohort feasibility assessment.

Do the data contain enough eligible participants to answer the research question?

Suppose we want to study whether sleep disorders are associated with a subsequent diagnosis of Alzheimer’s disease (AD).

Before estimating any association, we first need to know:

  • How many patients have a recorded sleep disorder?
  • How many of those develop AD?
  • What does the potential study cohort look like?

This is a very simple first step, but one that is surprisingly easy to overlook.

It’s exciting to wake up with a great research idea, spend weeks writing an analytic plan, and imagine the paper published in Science or NEJM. Then comes the unpleasant surprise: the data contain only a handful of eligible individuals or none at all. Another beautifully written analytic plan joins the collection in my cabinet that will never see daylight.

~ Based on (more than one) true story.

Translate the question into measurable definitions

Clinical questions are rarely stored directly in an EHR. Before writing any SQL, we need to translate the study question into explicit cohort definitions that the database can evaluate.

For this tutorial, our question is:

Among patients with sleep disorders, how many develop Alzheimer’s disease?

To answer that question, we first need to define what each component means in the data.

For this example:

  • Sleep disorder: any ICD-10 code beginning with G47.

  • Alzheimer’s disease (AD): any ICD-10 code beginning with G30.

  • Sleep disorder index date: the earliest recorded G47. diagnosis.

  • AD diagnosis date: The earliest recorded G30. diagnosis.

Because this is only a feasibility assessment, I intentionally start with simple definitions. Our goal is not to build a publication-ready cohort yet. We simply want to determine whether the available data contain enough potentially eligible patients to justify further work.

For simplicity, this tutorial uses the ICD-10 prefixed G47. and G30.. In a real study, disease definitions should be based on prespecified, clinically reviewed phenotype that specifies included codes, diagnosis settings, coding system, and validation rules.

This example uses fully synthetic EHR data consisting of three relational tables (patients, diagnoses, and encounters). The synthetic datasets and the R script used to generate them are available through the links at the top of this page and in the accompanying GitHub repository, so you can reproduce the entire workflow or create your own practice data.

Understand the source tables

Step 1. Create the sleep disorder cohort

Goal: Create one row per patient containing the earliest recorded sleep disorder diagnosis.

Before we ask whether patient later develop Alzheimer’s disease, we first need to identify the study cohort. Since patients may receive multiple sleep disorder diagnoses over time, we need a single index date for each patient

For this tutorial, we define the index date as the earliest recorded diagnosis with an ICD-10 code beginning with G47..

CREATE TABLE sleep_index AS
SELECT 
    PATID, 
    MIN(DX_DATE) AS SLEEP_DISORDER_INDEX_DATE
FROM diagnoses
WHERE ICD10 LIKE 'G47.%'
GROUP BY PATID;
SELECT *
FROM sleep_index
LIMIT 5

P0007 2019-02-22

GROUP BY PATID collapse multiple diagnoses (rows) into one per patient, while MIN(DX_DAT) identifies the earliest observed sleep disorder diagnosis.

Because we will use this cohort in subsequent steps, save it as a new table.

Verify the cohort

One habit worth having is to verify each intermediate table before moving on. At a minimum, I check that the table contains exactly one row per patient.

SELECT

    COUNT(DISTINCT PATID) AS n_unique_patients

If n_rows and n_unique_patients are different, something probably went wrong. The table may still contain duplicate patients or the query may not have reduced the data to the intended unit of analysis.

In this synthetic dataset, both values are 550, confirming that sleep_index contains one row per patient.

Combine two patient-level tables

Next, merge the AD information with the sleep disorder cohort.

Because we want to keep every patient with a sleep disorder, including those who never develop AD, we use a LEFT JOIN.

CREATE TABLE sleep_ad_cohort AS
SELECT 
    s.PATID,
    s.SLEEP_DISORDER_INDEX_DATE, 
    a.AD_INDEX_DATE,
    CASE
        WHEN a.AD_INDEX_DATE IS NOT NULL THEN 1
        ELSE 0
    END AS AD_STATUS
FROM sleep_index s
LEFT JOIN ad_index a 
    ON s.PATID = a.PATID;

The AD_STATUS variable simply indicates whether an AD diagnosis exists anywhere in the available EHR data.

  • AD_STATUS = 1: at least one AD diagnosis was observed.
  • AD_STATUS = 0: no AD diagnosis was observed.

At this stage, AD status should not be interpreted as incident Alzheimer’s disease. Some patients may have received an AD diagnosis before their sleep disorder diagnosis. We will address the temporal relationship between exposure and outcome in the next tutorial.

Step 3. Add patient characteristics

Goal: Build the final patient-level cohort and summarize its demographic characteristics.

At this point, the cohort contains the study variables needed to define sleep disorder and AD status. The final step is to attach patient-level demographic information so we can describe the potential study population.

Join the cohort with the patients table.

CREATE TABLE sleep_ad_cohort_with_demo AS
SELECT 
    s.PATID,
    s.SLEEP_DISORDER_INDEX_DATE, 
    s.AD_INDEX_DATE,
    s.AD_STATUS,
    p.BIRTH_DATE,
    p.DEATH_DATE,
    p.SEX,
    p.RACE
FROM sleep_ad_cohort s
LEFT JOIN patients p 
    ON s.PATID = p.PATID;

Because the patients table already contains one row per patient, this join should perserve the patient-level structure of the cohort.

As before, it’s worth verifying that no duplicate patients were introduced.

    COUNT(*) AS n_rows, 
    COUNT(DISTINCT PATID) AS n_unique_patients
FROM sleep_ad_cohort_with_demo;
1 records
n_rows n_unique_patients
550 550

Step 4. Summarise the cohort

The patient-level cohort is now complete!

Before moving on to more complex analyses, it is good practice to summarize the study cohort. A simple descriptive table helps confirm that the cohort looks reasonable and provides a snapshot of the patients included in the feasibility assessment.

Although SQL is excellent for cohort construction, I usually switch to R for descriptive statistics and ready-to-use table.

Let’s import the final table.

cohort_final <- DBI::dbGetQuery(
  con,
  "SELECT * FROM sleep_ad_cohort_with_demo"
)

Since age isn’t stored directly, calculate it from the date of birth and sleep disorder index date. Also, re-code value of AD_STATUS more readable.

cohort_final <- cohort_final %>%
  mutate(
    AGE_AT_SLEEP_DISORDER_DX = 
      as.numeric(
        as.Date(SLEEP_DISORDER_INDEX_DATE) - as.Date(BIRTH_DATE)
      )/365.25
  ) %>%
  mutate(
    AD_STATUS = case_when(
      AD_STATUS == 1 ~ "AD",
      AD_STATUS == 0 ~ "No AD"
    )
  )

Finally, summarise the cohort characteristics by AD status.

Interpretation

This preliminary cohort contains 550 patients with at least one recorded sleep disorder diagnosis.

Of these,

  • 101 (18.3%) have at least one recorded Alzheimer’s disease diagnosis
  • 449 (81.6%) do not have any recorded Alzheimer’s disease diagnosis.

The descriptive table also allows us to quickly assess whether the demographic characteristics appear reasonable before investing additional effort in refining the cohort or developing models.

Conclusion

At this point, we have answered the original feasibility question:

Can these data support the proposed study?

The answer appears to be yes. We successfully identified a patient-level cohort, linked potential outcomes, and summarized the study population. However, this cohort is still intentionally simple and small. In the next tutorial, we’ll refine it by introducing baseline periods, follow-up requirement, and temporal ordering between exposure and outcome.

```{r}
cohort_final <- cohort_final %>%
  mutate(
    AGE_AT_SLEEP_DISORDER_DX = 
      as.numeric(
        as.Date(SLEEP_DISORDER_INDEX_DATE) - as.Date(BIRTH_DATE)
      )/365.25
  ) %>%
  mutate(
    AD_STATUS = case_when(
      AD_STATUS == 1 ~ "AD",
      AD_STATUS == 0 ~ "No AD"
    )
  )
```

```{r}
table1(~AGE_AT_SLEEP_DISORDER_DX+SEX+RACE | AD_STATUS, data = cohort_final)
```
